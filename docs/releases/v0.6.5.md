# Meowcal Sub v0.6.5

A refinement release. The capture region can now cover the whole video, and the
app works out for itself which horizontal bands of text inside it are subtitles.
Scene text, signs, static overlays and end credits are recognised and then held
back rather than translated.

There is deliberately no new user-facing feature here, and on an episode that is
nothing but dialogue this release is indistinguishable from 0.6.4. The
measurements below say so plainly, because the value is in what stops happening
on the frames where 0.6.4 got it wrong.

As in the previous two releases, everything was measured against recorded
sessions rather than reasoned about.

## Why a tall region could not work before

0.6.4 joined every line inside the capture region into one string and translated
it as a unit. A region tall enough to catch two possible subtitle positions
therefore also caught whatever sat between them, and sent it along as dialogue.
That release's answer was to reject the whole frame when the join grew longer
than a subtitle cue, which stopped the nonsense but also stopped the dialogue
sitting beside it.

Windows OCR reports a bounding rectangle per word, and the pipeline had always
discarded it. Recovering that geometry is what makes a different answer possible:
group the recognised lines into horizontal bands, and judge each band separately.

## Choosing which band is the subtitle

Two signals decide it, both measured over a rolling ninety-second window:

- **Horizontal scatter.** Subtitles are centred; a band whose lines wander more
  than 15% of the frame width is scene text that happens to be at that height.
- **How often the band turns over.** Dialogue changes between about 10 and 55
  times a minute of screen time. Below that is a sign or a frozen screen. Above
  it is end credits, which hold their position perfectly and would otherwise pass
  the scatter test.

Vertical position is deliberately not one of them. Subtitles sit at the bottom
around nine times in ten, and a rule that encoded that would score well on
average while failing exactly the case this release exists to serve.

Two lines cannot be told apart by comparing their text, because Windows OCR
misreads roughly one character in three and two reads of a motionless subtitle
disagree. A band is judged to be showing the same cue when its width and
character count are both close to the previous frame's, which survives a wrong
glyph.

## Judged continuously, not once

The window is ninety seconds rather than the whole session, because a band
changes character partway through: the band carrying dialogue for twenty minutes
carries end credits afterwards, and a whole-session average reads it as neither.

A band that has been a subtitle is given eight frames of disagreement before it
is demoted, but is promoted again immediately. A subtitle that vanishes for a
second is worse than a stray line that lingers for two.

A band with too little history is included rather than excluded — absence of
evidence, not evidence of absence — so the first seconds after starting may show
text that later settles out. A band seen fewer than three times is excluded,
since one sighting is not a band.

## What it changes, measured

Two recorded sessions, 38.8 and 44.7 minutes, replayed through the shipped
tracker:

| | frozen-screen session | normal episode |
| --- | --- | --- |
| Recognised lines never sent to the translator | 62% | 37.5% |
| Translation calls avoided | 11% | 21% |
| Subtitle screen time lost | 2–11% | 5–7% |

The gap between the first two rows is the honest part. Junk text never cost a
model call of its own — 0.6.4's duplicate detection already suppressed repeated
static text. What it did instead was pad every prompt and re-trigger dialogue
that had not changed. Dropping 37% of the lines removes about 21% of the calls.

Rejections for text being too long fall as well, from roughly 41% of
text-bearing frames to 35% on the normal episode. That figure is approximate —
it assumes each band keeps one verdict for the whole session, which understates
the improvement during credits — but the direction and the rough size hold.

The first session spent half its length on a frozen screen, which is why its
numbers are so much larger; treat the normal episode as the representative one.

## What it costs

Between 5% and 7% of subtitle screen time on the main bottom bands, weighted so
that losing a two-frame flicker does not count the same as losing a line. Short
cues are the ones at risk, because a band needs a few sightings before it is
trusted. This is a real regression against 0.6.4 for anyone using a region
narrow enough that 0.6.4 was already correct, and narrowing the region remains
the way to avoid it.

## Known limitations

- Each band's translation is still shown in the single overlay rather than near
  the text it came from, so a top and a bottom subtitle arrive in the same place.
  The grouping needed to fix that is preserved through the pipeline; the
  rendering is tracked as issue #57.
- Windows OCR splits some characters into their radicals, and 0.6.4 confirmed the
  app cannot fix that by preprocessing. A different recognition engine is the
  remaining option, tracked as issue #53.
- Capture is fixed to the primary monitor while the overlay covers every display,
  so a capture region placed on a secondary monitor reads the wrong pixels.
  Tracked as issue #52. Single-monitor setups are unaffected.
- Only one capture region is supported. A tall region is now selected from rather
  than rejected, which is not the same as supporting several separate areas.
- Text that is too long for a subtitle is still rejected, and band selection
  reduces that without removing it. A region catching a page of text will still
  go quiet on the frames where the kept bands alone exceed a cue.
- Translation latency is dominated by the local model. The overlay diagnostics
  panel reports total and model time per line.
- The installer asks whether to uninstall the previous version before upgrading.
  "Do not uninstall" is the correct answer and the default.

## Before installing

- Windows 11 is the supported target.
- Choose ARM64 for Snapdragon/ARM Windows PCs and x64 for Intel or AMD PCs.
- Installers are not code-signed. Windows SmartScreen may show an
  unknown-publisher warning; verify downloads against `SHA256SUMS.txt`.
- The local translation runtime and model require a one-time download of about
  1.1 GB.

## Validation status

The full automated repository gate passed: Rust format, clippy, unit and IPC
integration tests, frontend format, lint, typecheck, production build, unit
tests, the browser-to-Rust smoke, and the maintainability ratchet.

An ARM64 build of this code was installed from its own package and run on
Windows 11 build 26200 against live playback with a tall capture region. The
band thresholds were calibrated on one recorded session and then checked against
a second from a different source, which is what exposed end credits passing the
scatter test and led to the upper bound on turnover.

The two sessions are one language pair, one machine and one pair of streaming
sources. Treat the percentages as an indication rather than a benchmark.

The x64 package is built by the same script and has not had an equivalent check.
