# Meowcal Sub v0.6.6

Meowcal Sub can now update itself. **Settings → Updates → Check for updates**
asks GitHub whether a newer release exists; if one does, a second press
downloads it, verifies it, upgrades in place, and reopens the app.

Nothing about this is automatic. The app never checks on its own, never
downloads in the background, and never installs without being told to twice.

There is no other user-facing change in this release.

## Why this exists

Updating meant noticing a release on GitHub, working out whether your PC is x64
or ARM64, downloading the matching installer, and answering an installer
maintenance page that asked whether to uninstall the previous version first.
Nobody does that reliably, so the fixes shipped in 0.6.3, 0.6.4 and 0.6.5 have
been reaching almost nobody.

## What it does when you press install

1. Stops translation if it is running, saves the window position, and shuts down
   the local engine and any overlay process.
2. Downloads the installer built for this PC's architecture.
3. Verifies it against a signature this app was compiled with. A download that
   does not match is rejected and nothing is installed.
4. Closes Meowcal Sub, upgrades in place without the uninstall prompt, and
   reopens it.

Settings, onboarding state, the installation directory, and the downloaded
engine and model are all preserved. The upgrade replaces program files only.

## What had to be fixed first

Every packaging run had been printing a warning that the updater would not be
able to update the package: `__TAURI_BUNDLE_TYPE variable not found in binary`.
The Tauri CLI was not declared anywhere in the repository, so builds used
whatever happened to be installed on the machine — in practice a version behind
the `tauri` crate, and too old to write that marker. The CLI is now pinned in
`package.json` and kept level with the crate.

The release workflow used to assert it found four installers. It now names what
it expects per architecture, including the update signature, so a run that
produced two copies of one architecture cannot pass as a complete release.

## The part that is not solved

The installers are still not code-signed. The signature the updater checks
proves a download is the file this project published and has not been tampered
with in transit; it is not an Authenticode certificate, and Windows does not
know about it. Applying an update can therefore raise the same SmartScreen
unknown-publisher prompt as a fresh install — meeting that prompt more often is
a real cost of making updates easier. Code signing is tracked separately.

## Known limitations

- The check is manual by design. There is no notification when a release
  appears; you have to look.
- Downgrading is not offered. The app installs the latest published release or
  nothing.
- The whole installer is downloaded each time, roughly 22–25 MB. There are no
  delta updates.
- Each band's translation is still shown in the single overlay rather than near
  the text it came from, so a top and a bottom subtitle arrive in the same
  place. Tracked as issue #57.
- Windows OCR splits some characters into their radicals, and 0.6.4 confirmed
  the app cannot fix that by preprocessing. Tracked as issue #53.
- Capture is fixed to the primary monitor while the overlay covers every
  display. Tracked as issue #52. Single-monitor setups are unaffected.
- Only one capture region is supported.
- Translation latency is dominated by the local model.

## Before installing

- Windows 11 is the supported target.
- Choose ARM64 for Snapdragon/ARM Windows PCs and x64 for Intel or AMD PCs.
- Installers are not code-signed. Windows SmartScreen may show an
  unknown-publisher warning; verify downloads against `SHA256SUMS.txt`.
- The local translation runtime and model require a one-time download of about
  1.1 GB.
- This is the first release that can be updated from inside the app. Reaching
  it still requires installing it by hand; releases after it will not.

## Validation status

The full automated repository gate passed: Rust format, clippy, unit and IPC
integration tests, frontend format, lint, typecheck, production build, unit
tests, the browser-to-Rust smoke, and the maintainability ratchet.

An ARM64 build of this code was packaged and installed on Windows 11 build
26200, and the packaging run no longer emits the bundle-type warning.

The x64 package is built by the same script and has not had an equivalent
check.
