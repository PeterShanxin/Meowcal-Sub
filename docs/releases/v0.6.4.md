# Meowcal Sub v0.6.4

A stability release. The app no longer leaves a multi-gigabyte process running
after it closes, a large capture region no longer takes the window down with it,
and the pipeline keeps reading the screen while the model is busy.

As in 0.6.3, everything below was diagnosed from session logs of a
Chinese-to-English episode rather than reasoned about, so the causes are
recorded alongside the fixes.

## The translation engine no longer outlives the app

The local translation engine is a separate process holding the model in memory —
around 1.5 GB once loaded. It was stopped on the way out, but only on the clean
exit path. Windows does not tie a child process's lifetime to its parent's, so
every other way the app could end left the engine running:

- the installer closing the running app to replace its files,
- Task Manager, or any other forced termination,
- a crash, or the web view taking the process down with it,
- signing out or shutting down Windows.

Each of those stranded one engine. Worse, the next launch could not reuse it —
the stranded process still held the network port — so it started another. They
accumulated one per crash. Six had built up on the development machine, one of
them holding 1.17 GB, which was enough to make the Rust compiler itself run out
of memory during a build.

Every child process is now placed in a Windows job object configured to
terminate its contents when the app's handle to it closes. No cleanup code has
to run for this to work, which is the point: the paths that leaked were exactly
the paths where the app's own code never got the chance.

Engines stranded by earlier versions are cleaned up at startup, before the app
starts its own. A process is only ever a candidate if it is running this
install's own managed engine file and its parent process is gone. Terminating by
program name was explicitly not an option — an unrelated `llama-server.exe` from
some other tool is not this app's to end — and the check deliberately errs
toward leaving a process alone, so a second running copy of Meowcal Sub never
loses its engine.

## A large capture region no longer kills the window

Selecting a region covering most of the screen turned the window white. The app
kept translating and the tray icon kept responding, which made it look like a
front-end bug; it was not. A near-full-screen region is around 20 MB of pixel
data per frame, copied several times per recognition, four times a second. The
web view's renderer ran out of memory and was killed by Windows.

The diagnosis is in the log verbatim, because the app read its own crashed
renderer off the screen it was capturing: `Aw, Snap! ... Error code: Out of
Memory`, alongside five OCR failures reporting `0x8007000E`.

Frames are now reduced before recognition. On a high-DPI display they are
brought back toward one logical pixel per physical pixel, and a hard ceiling of
two million pixels applies underneath that. Both use area averaging rather than
dropping pixels, which measurement showed matters: point sampling produced worse
recognition at 0.75 scale than at either 1.0 or 0.5, because dropped rows land
unpredictably across the strokes of a glyph.

Accuracy holds down to about 0.4 scale and collapses at 0.3, where glyph height
crosses roughly twenty pixels. The shipped reduction stays well above that.

## The pipeline keeps reading while the model works

Translation ran inline in the capture loop, so nothing was captured, recognised
or displayed while the model was working. A single slow call stopped the whole
pipeline.

Translation now runs off the loop. Capture continues at its normal interval
during a translation, and a frame arriving while one is in flight is skipped
rather than queued — for subtitles the newest line is the only one worth having.

## Stalls and "translation service unavailable"

Two separate causes, both in the model client:

- An individual attempt was only given a deadline when extra context was
  attached to the request. Context is off by default, so in the default
  configuration an attempt could run to the full thirty-second total. One
  session shows a 27.6-second freeze with no captures at all.
- Retries were decided from an error message built only from the top-level
  error, which never includes the underlying cause. A dropped keep-alive
  connection — routine when the engine has been idle — therefore looked like a
  permanent failure and surfaced as "service unavailable" instead of being
  retried.

Every attempt is now bounded, the error message carries the full cause chain,
and the same text the user sees is what the retry decision reads. Deterministic
failures are still never retried.

## One line, one translation

0.6.3 introduced re-read detection. Replaying 569 real translated lines from a
session log found three ways a re-read still slipped through: a re-read that
lost characters fell under the length floor for comparison, the floor itself was
too high for short lines, and a read that grew by a single stray glyph counted
as the subtitle being extended. Closing all three suppressed 65 further
retranslations — 11.4% of the sample — with no genuine dialogue lost.

29 pairs remain that differ by roughly half their characters. Those are beyond
any threshold; see the OCR note below.

## Text too long to be a subtitle

A capture region covering more than the subtitle hands back every line inside it
joined into one sentence, and that went to the model as dialogue — one session
log has a memory readout being translated. It costs a full model call, holds the
translation slot while real dialogue goes past, and puts a paragraph of
unrelated text over the video.

Lines longer than a subtitle cue are now dropped, and the overlay says so rather
than going quiet, because a region catching too much is a region to narrow.
There are two limits, because the same sentence needs roughly twice the
characters in an alphabetic script as in an ideographic one: 50 characters for
Chinese, Japanese and Korean, 100 otherwise. Broadcast practice puts a full
two-line cue near 40 and 84 respectively, so both sit above anything a real cue
produces. The script is judged from the text that was actually recognised, not
from the configured source language.

## What we measured about OCR accuracy

Issue #53 asks whether the app's own image preprocessing is what splits Chinese
characters into their radicals. It is not, and the answer is now on record
rather than assumed.

Four preprocessing variants were run over the same frames during live playback —
319 frames, 151 carrying text — and scored against a hand-transcribed ground
truth. Binarization turned out to be content-dependent rather than harmful: it
lost 4.9 points against one background and gained 15.0 against another. The
shipped default is therefore unchanged.

The decisive observation was separate from the scores. Radical splitting appears
under every variant, including handing Windows OCR the frame exactly as
captured, so the splitting happens inside the recognizer.

Character accuracy on difficult frames measures 66–74%. Roughly one character in
three is wrong before the text reaches the translator, and that — not any filter
in this app — is the ceiling on subtitle quality today. The sample is three
subtitle runs on one episode and one machine, so treat it as an indication
rather than a benchmark.

## Known limitations

- Windows OCR splits some characters into their radicals, and this release
  confirms the app cannot fix that by preprocessing. A different recognition
  engine is the remaining option, tracked as issue #53.
- Capture is fixed to the primary monitor while the overlay covers every
  display, so a capture region placed on a secondary monitor reads the wrong
  pixels. Tracked as issue #52. Single-monitor setups are unaffected.
- Only one capture region is supported. A tall region that covers several
  possible subtitle positions will now be rejected as too long rather than
  translated as nonsense, which is an improvement but not the same as
  supporting more than one area.
- Translation latency is dominated by the local model. The overlay diagnostics
  panel reports total and model time per line.
- The installer asks whether to uninstall the previous version before upgrading.
  "Do not uninstall" is the correct answer and the default.

## Before installing

- Windows 11 is the supported target.
- Choose ARM64 for Snapdragon/ARM Windows PCs and x64 for Intel or AMD PCs.
- Installers are not code-signed. Windows SmartScreen may show an
  unknown-publisher warning; verify downloads against `SHA256SUMS.txt`.
- The local translation runtime and model require a one-time download of about
  1.1 GB.

## Validation status

The full automated repository gate passed: Rust format, clippy, unit and IPC
integration tests, frontend format, lint, typecheck, production build, unit
tests, the browser-to-Rust smoke, and the maintainability ratchet.

An ARM64 build of this code was installed from its own package and run on
Windows 11 build 26200. The process lifetime work was checked against the live
process table rather than only in tests: with the owning app running, the
cleanup pass correctly left its engine alone; after the installer closed that
app, the same pass identified the stranded engine and the next launch ended it,
which the session log records by process ID. The job object was separately
confirmed to terminate a child when its parent is forcibly killed, against a
control that survives the same treatment without it.

The x64 package is built by the same script and has not had an equivalent check.
